# GitHub Provider

## Overview

`src/providers/github/` is the GitHub forge adapter: it implements the platform-agnostic `CodeHost`, `IssueTracker`, and `BoardManager` ports (defined in `src/providers/types.ts`) on top of the `gh` CLI and the GitHub REST/GraphQL APIs, and it supplies GitHub's `TokenProvider` and bootstrap `GitIdentity` implementations to the git core. It is the only package permitted to shell out to `gh`, and it owns every GitHub-specific naming, parsing, and credential convention so that `src/git` and the rest of the codebase stay forge-neutral.

## Responsibilities

- **Command execution.** `ghCommandRunner.ts` is the adapter's sole route to a child process: it wraps `GitContext.exec`, always runs from the framework-root cwd (repo identity travels in the command string, not the cwd), and layers a per-command credential overlay resolved through `GitContext.commandEnv` for a given `CredentialPurpose` (`'default'` or `'alternateIdentity'`).
- **Command string / response parsing.** `commands/issueCommands.ts`, `commands/prCommands.ts`, `commands/labelCommands.ts`, `commands/secretCommands.ts`, and `commands/boardCommands.ts` build the literal `gh issue ...` / `gh pr ...` / `gh api ...` / `gh api graphql ...` command strings (and, for board commands, parse the GraphQL JSON responses). `ghIssueParsers.ts` and `ghPrParsers.ts` are pure parsers that turn `gh`'s JSON/REST output into the adapter's domain shapes (`domain/issue.ts`, `domain/pullRequest.ts`); they throw on malformed JSON and apply no error policy of their own.
- **Bound leaf APIs.** `ghIssueApi.ts` and `ghPrApi.ts` bind the 14 issue and 13 PR operations to one `owner/repo` over a `GhCommandRunner`. `ghRepoApi.ts` composes those two plus label/secret/board operations into one `GhRepoApi` (35 operations) over a single `GitContext`. These are deep-import-only — never re-exported from `index.ts` — because a bound view over an existing context selects no identity.
- **Port implementations.** `githubCodeHost.ts` (`CodeHost`), `githubIssueTracker.ts` (`IssueTracker`), and `githubBoardManager.ts` (`BoardManager`) are classes constructed from a `GitContext` plus a `RepoIdentifier`; each binds `createGhRepoApi`/`createGhCommandRunner` once, maps raw GitHub shapes to platform-agnostic ones via `mappers.ts`, and logs through an injected `Logger` (default `consoleLogger`).
- **GitHub App auth.** `appAuth.ts` mints and caches (in-memory, per `owner/repo`, 5-minute expiry buffer) GitHub App installation tokens via the JWT → installation-lookup → token-exchange dance, talking to the GitHub REST API over `curl`.
- **Identity and token resolution.** `githubIdentity.ts` resolves a bootstrap `GitIdentity` and parses GitHub remote URLs; `githubTokenProvider.ts` and `tokenResolver.ts` resolve a `GH_TOKEN` value for a given repo and credential purpose; `ghAuthToken.ts` is the CLI fallback of last resort.
- **Clone URL rewriting.** `cloneUrl.ts` converts an HTTPS GitHub clone URL to SSH form.
- **Cross-checks.** `contextBinding.ts` provides `assertContextBoundTo`, used by all three port factories to refuse a `GitContext` bound to a different repository than the caller's declared `RepoIdentifier`.

## Contracts & Invariants

- **`gh` is only issued here.** Every `gh`/`curl` invocation in the adapter goes through `GitContext.exec` (via `ghCommandRunner`) or, for GitHub App auth, `execFileSync('curl', ...)` inside `appAuth.ts`; nothing in this package imports `child_process` directly except `appAuth.ts` and `ghAuthToken.ts`, both of which are explicitly documented as guard-exempt, pre-context spawns.
- **Token resolution order (`tokenResolver.ts` / `resolveContextToken`)**: (1) if the GitHub App is configured, mint and return an installation token bound to `owner/repo` — any failure (e.g. app not installed) propagates loudly rather than falling back; (2) else if a PAT is supplied and non-blank, return it; (3) else if `gh auth token` returns non-blank output, return it; (4) otherwise throw `"resolveContextToken: no veracious token for {owner}/{repo}"`. `process.env.GH_TOKEN` is never read as a source — this is deliberate, since ambient `GH_TOKEN` fallthrough was the root cause of a class of "wrong repo" credential-bleed incidents.
- **`createGitHubTokenProvider` (`githubTokenProvider.ts`)** wraps `resolveContextToken` as a `TokenProvider`: for `purpose === 'alternateIdentity'` requests it returns a separately-injected `alternateIdentityPat` when non-blank, else falls back to the normal resolution order; all inputs (`pat`, `alternateIdentityPat`, `isAppConfigured`, `mintInstallationToken`, `ghAuthToken`) are injected — the provider itself reads no environment variable and holds no cache (the only caching on this path is `appAuth.ts`'s expiry-aware installation-token cache).
- **`resolveBootstrapGitIdentity` (`githubIdentity.ts`)** resolves a git author/committer identity before any `GitContext` exists, in order: (1) GitHub App bot identity (`{appSlug}[bot]` / `{appId}+{appSlug}[bot]@users.noreply.github.com`) if the App is configured; (2) `GIT_AUTHOR_*`/`GIT_COMMITTER_*` env vars; (3) `git config user.name`/`user.email`; (4) the built-in `ADW_BOT_FALLBACK_IDENTITY` (`ADW Bot` / `adw-bot@users.noreply.github.com`) — it never returns an empty field. App-configuration state is resolved from `deps.appConfig` when supplied (`undefined` = "look at the environment triple", `null` = "no App, even if the env carries `GITHUB_APP_*`", present-and-complete = derive from it) or from an explicit `deps.isAppConfigured`, which takes precedence over `appConfig` when both are given.
- **`getInstallationToken` (`appAuth.ts`)** requires `isGitHubAppConfigured(config)` to have been checked by the caller; it throws a named error (rather than a raw `TypeError`) if `appId`/`privateKeyPath` is missing. It caches tokens and installation IDs per `owner/repo` and refreshes 5 minutes before expiry. The bearer credential is always sent to `curl` via `--config` stdin, never as a CLI argument, so it cannot leak into a thrown `execFileSync` error or the process table; all failure/error text is passed through `redactBearerTokens` and, for response bodies, restricted to GitHub's own `message` field.
- **Repo binding.** `createGitHubCodeHost`, `createGitHubIssueTracker`, and `createGitHubBoardManager` all call `assertContextBoundTo(ctx, repoId, <factoryName>)`, which throws if the `GitContext`'s `owner`/`repo` (case-insensitively) does not match the given `RepoIdentifier`; `platform` is not compared.
- **PR selection.** `selectPreferredPR` prefers the most-recently-updated `OPEN` PR for a branch, falling back to the most-recently-updated PR overall only when none are open (a stale closed/merged PR must never win over a live open one).
- **PR approval.** `parsePRApprovalState` trusts `reviewDecision === 'APPROVED'` outright, treats any other non-empty `reviewDecision` as a refusal, and only falls back to `isApprovedFromReviewsList` (latest substantive review per author must all be `APPROVED`) when `reviewDecision` is null/empty. `approvePR` runs under the `'alternateIdentity'` credential purpose because GitHub forbids a bot from approving its own PR.
- **Board status moves.** `moveIssueToStatus` walks project lookup → item lookup → status-field lookup → mutation, short-circuiting to `false` on any lookup failure or missing data, and to `true` early if the item is already at the target status; status names match case-insensitively, with exact match preferred over a fuzzy "includes" match.
- **`parseGitHubRemoteUrl`** is the single source of truth for GitHub remote URL parsing, matching both `https://github.com/owner/repo[.git]` (including credentialed URLs) and SCP-style `git@github.com:owner/repo[.git]`; it returns `null` (not a throw) for anything else.
- **Clone URL rewriting** only rewrites URLs that start with `https://github.com/`; anything else (SSH, another forge, empty) is returned unchanged.

## Configuration

- GitHub App identity (`appId`, `appSlug`, `privateKeyPath`) is injected via `GitHubAppConfig`; this package never reads `GITHUB_APP_ID`/`GITHUB_APP_SLUG`/`GITHUB_APP_PRIVATE_KEY_PATH` from `process.env` itself — that is the caller's job (e.g. the ADW wiring shim), except that `resolveBootstrapGitIdentity`'s default behavior (when no `appConfig`/`isAppConfigured` is injected) does look at that same env triple via `deps.env ?? process.env`.
- `AppAuthDeps.apiBaseUrl` overrides the GitHub API origin (default `GITHUB_API_BASE_URL = 'https://api.github.com'`); `AppAuthDeps.runCurl` overrides the curl runner for hermetic testing.
- `GitHubCodeHostDeps.canApprovePullRequests` is a caller-supplied capability check consulted by `canApprovePullRequests()`; it defaults to always returning `false`.
- `GitHubIssueTrackerDeps.onStatusMoved` and `resolveLabelDefinition` let a caller hook board-status-move notifications and lazy label-creation metadata without the tracker knowing about Slack or a specific label color scheme.
- `GitHubBoardManagerDeps.logger` / `GitHubCodeHostDeps.logger` / `GitHubIssueTrackerDeps.logger` all default to `consoleLogger` from `src/git`.
- `GitHubTokenProviderInput` / `ResolveContextTokenInput` take `pat`, `alternateIdentityPat`, `isAppConfigured`, `mintInstallationToken`, and `ghAuthToken` as plain injected values/functions — no environment reads inside `githubTokenProvider.ts` or `tokenResolver.ts`.

## Gotchas

- `ghIssueApi.issueLabels` is a rename of the historically misnamed `issueHasLabel` GitContext method; it still runs the same `gh issue view --json labels` command under the hood.
- `createIssueCmd`/`createPRCmd`/etc. build shell command *strings*, not argv arrays — bodies are always passed via `--body-file -` with the actual content delivered on stdin (`input`), not interpolated into the command string.
- `createPRCmd` always passes `--head` explicitly; letting `gh` infer the head from the current working directory would silently target the wrong branch (the context's base path sits on the default branch), producing an empty-diff PR.
- Several `gh api graphql` calls (board moves, `runGraphQL`, `approvePR`, project/label GraphQL queries) always run under the `'alternateIdentity'` credential purpose — swapping identities on some of these calls without a good reason (or omitting the purpose) can silently pick up the wrong token in the `credentialEnv` overlay.
- `getAuthenticatedUser()` on `GitHubCodeHost` memoizes its result (including `null` on failure) for the lifetime of the instance — a `GH_TOKEN`/identity change after construction will not be reflected without a new instance.
- `resolveContextToken`/`createGitHubTokenProvider` never fall back to `process.env.GH_TOKEN`; if none of App/PAT/`gh auth token` resolve, the call throws rather than silently picking up an ambient token — this is intentional (see Contracts) but means a bare "logged into `gh` globally, no PAT, no App" environment must still have `gh auth token` succeed, or every credentialed call fails.
- `appAuth.ts`'s token and installation-ID caches are process-lifetime module-level `Map`s with no external invalidation hook besides `clearAppAuthCaches()` (test-only) — a revoked or reconfigured installation is not detected until the cached token's expiry buffer is hit.
- `ghAuthToken()` and `appAuth.ts`'s curl calls are the only direct child-process spawns in this package and are explicitly exempted from the repo's git/gh guard by directory; anything else in this adapter that needs to run a process must go through `ghCommandRunner`/`GitContext.exec`.
- `mapPRListItemToPullRequest` only has `number` and `headBranch` available from `gh pr list`'s limited projection, so `title`, `body`, and `targetBranch` are always empty strings and `state` is hardcoded to `'OPEN'` (the listing only ever returns open PRs).
- `parsePRDetails` derives `issueNumber` from an `Implements #<n>` pattern in the PR body first, falling back to parsing an `issue-<n>` token out of the head branch name — a PR that doesn't follow either convention resolves `issueNumber: null`.
